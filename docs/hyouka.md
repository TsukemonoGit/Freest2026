## 評価

全体として、**「身近な疑問 → 仕組みを知る → 自分で回路を作る → 実際の信号を取る → 解析する → 目的を思い出す」**という流れは成立しています。

特に強いのは、後半の解析です。単に「424ビットでした」で終わらず、

**生データ → 0/1化 → 8ビット単位 → 温度だけ変えて比較 → 14・15バイトを特定 → 温度の規則を予測 → 実測で検証**

という、かなりきれいな「仮説 → 実験 → 検証」になっています。

一方で、**発表として見ると「技術的に面白いところ」と「発表で聞き手に必要なところ」の比重が少しずれています。**

## 最終的な構成

私なら発表の章立てをこうします。

**1. やりたいこと**
エアコンをスマホから操作したい

**2. どうやって実現する？**
リモコンの代わりを自作する

**3. 赤外線通信を知る**
MARK / SPACE / 38 kHz

**4. 受信回路を作る**
Pico + 赤外線受信モジュール

**5. 信号を取ってみる**
生データ → 0/1 → 424ビット

**6. 424ビットを読み解く**
8ビットずつ比較

**7. 温度の場所を探す**
14・15バイト

**8. 仮説を立てて検証する**
1℃ → 4増える → 16℃を予測 → 的中

**9. ここで目的を思い出す**
全部解析する必要はない

**10. 成果と今後**
受信・解析 → 信号再現 → 送信 → スマホ操作

この構成なら、**「電子工作をしました」ではなく「目的を達成するために、疑問を一つずつ実験で解決した研究」**として見せられます。

なお、現状の資料では実際の「送信」「スマホ操作」はまだ今後の段階なので、そこを**完成した成果として発表する表現にはしない**ほうが安全です。資料自身も最後に「今後は送信信号を作ってみたい」としています。

修正点：

* コードは「読むもの」ではなく、**実際にどの程度の処理を自分で書いたかを示す資料**として評価する
* プログラミング知識がない聞き手にも、**思考過程を省略せず再現可能な形で伝える**方針に合わせる
* 「コードを削る」のではなく、**コード以外の説明部分を整理する**方向に変更する
* GitHub掲載を前提に、発表では「何を考えて、なぜそのコードを書いたか」を説明する

この前提なら、前の評価は一部変えたほうがいいです。

### コードの見せ方

今のように**コードを小さく載せて、「これだけの処理を書いた」という存在感だけ出す**のは成立しています。

むしろ重要なのは、コードそのものではなく、その前後です。

例えばpage27なら、

> 「赤外線を受信したら、その信号が変化した時刻を記録するプログラムを書きました。」

↓ 小さくコード

> 「この時点では、まだ信号の意味は分かりません。まずは観察することにしました。」

という構成。

これなら、プログラムを知らない人にも、

**目的 → 考えたこと → 実装 → 結果 → 次に考えること**

が追えます。

# GitHubについて

これはかなり相性がいいです。

例えばコードを載せたページの隅に、

> **使用したコードはGitHubに公開しています**

と小さく書いておく。

そして発表では、

> 「コード自体はGitHubに公開しているので、今回はコードの中身を読むのではなく、何を考えてこの処理を書いたのかを説明します。」

と最初に一度だけ宣言する。

これなら、

**発表：思考過程を追う**
**GitHub：実装を再現する**

という役割分担になります。

## この方針なら、発表の評価基準も変わる

この発表で重要なのは、

**「最終的に何ビット解析できたか」**

だけではなく、

**「聞き手が、自分でも同じ手順を試せるくらい、調査の過程を追えるか」**

です。

その観点では、今の

> 生データ
> → 0/1化
> → 424ビット
> → 8ビット単位
> → 温度だけ変更
> → 変化位置を探す
> → 候補を考える
> → 規則を探す
> → 予測
> → 実測

という流れは、かなり残す価値があります。

逆に削る候補は、**思考に直接関係しない説明**です。

例えば、

* Wi-Fi / Bluetooth / 赤外線の一般的な比較
* 部品の細かい仕様説明
* 抵抗のカラーコードの細部
* 開発環境の細かいセットアップ手順

など。

つまり、

> **コードは残す。思考も残す。一般知識の説明を削る。**

という整理が、今回の発表には一番合っています。

# 発表原稿：「帰宅即快適」を自作する
## ～赤外線通信を理解して、スマホから操作する～ 第一部：受信・解析編

---

### P1 表紙
今日は「帰宅即快適を自作する」という自由研究を発表します。テーマは、赤外線通信の仕組みを理解して、最終的にスマホからエアコンを操作できるようにする、というものです。

### P2 やりたいこと／制約
やりたいことはシンプルで、「家のエアコンをスマホから操作して、帰宅した瞬間に快適な温度にしたい」というものです。ただし条件がいくつかあります。アパート備え付けのエアコンなので本体は改造できません。また純正Wi-Fiアダプターは約15,000円と高く、電子工作もほぼ初心者ではんだ付けキットすら持っていません。持っている部品はできるだけ使い、足りないものだけ買う、という縛りで進めます。

### P3 エアコン操作の自動化（方式の比較）
自動化の方法を3つ比較しました。純正Wi-Fiアダプターは確実だけど工事費含めて高い。SwitchBotハブは手軽だけどカスタマイズに制限がある。そこで選んだのが、Raspberry Pi Pico 2 WHを使って赤外線受信機を自作する方法です。値段は約3,000円と安く、何より「遊びがい・学びがいがある」。たのしいは正義、ということで、これで行くことにしました。

### P4-5 構成
発表は第一部「受信・解析編」と第二部「送信・スマホ対応編」に分かれます。今日お話しするのは第一部です。赤外線通信の基礎知識から始めて、部品選定、開発環境構築、そして実際の受信・解析まで進めます。

### P7 リモコンってどうやってなにしてるの？
そもそもリモコンは、赤外線を使った一方向の無線通信をしています。Wi-FiやBluetoothと比べると、通信距離は短く速度も遅いですが、その分コストが低く、構造もシンプルで、部屋の外に信号が漏れにくいという特徴があります。ネットワークに繋がっていないので、セキュリティの観点でもリスクが限定的です。

### P8 赤外線リモコンって何？
リモコンはMARKとSPACEという2種類の期間の組み合わせでデータを表現しています。MARKは赤外線LEDを38kHzで点滅させている期間、SPACEは消灯している期間です。この組み合わせパターンが「冷房ON、設定温度28℃、風量自動」のような命令になります。

### P9 なぜON/OFFではなく高速点滅させるの？
太陽光や照明にも赤外線は含まれているので、単純なON/OFFだと環境光と区別がつきません。そこで約38kHzで高速点滅させることで、環境光とリモコンの信号を見分けられるようにしています。38kHzという数字自体に物理的な理由はなく、区別しやすく回路も作りやすいから、という理由だそうです。

### P10 やること
今回やることは大きく2つ。1つ目はリモコンの信号を「学習」すること。2つ目はその信号を「再現」してエアコンを操作することです。今日はこのうち「学習」、つまり受信と解析の部分をお話しします。

### P11 マイコンの選定
マイコンにはRaspberry Pi Pico 2 WHを選びました。理由は、赤外線をマイクロ秒単位で正確に扱える、Wi-Fiが内蔵されている、3.3Vで部品を揃えやすい、ブレッドボードですぐ試せる、という4点です。ESP32など他の候補もありましたが、PIOという仕組みでタイミング制御が柔軟にできる点が決め手になりました。

### P12-13 赤外線受信回路を考える／データシートを読む
やりたいことから逆算して、必要な部品は「赤外線受信モジュール」と分かりました。ここで重要なのが、データシートという部品の公式ルールブックを読むことです。確認すべきは電源電圧、ピン配置、対応周波数、出力論理の4点です。

### P14-16 データシートを実際に読んでみる
実際にPL-IRM1838Bというモジュールのデータシートを開いてみると、正直、情報量に圧倒されました（笑）。でも落ち着いて必要な項目だけ拾っていきます。動作電圧は2.7～5.5V、入力周波数は37.9kHzなのでPicoの3.3Vと38kHzのリモコンにぴったり合います。ピン配置も確認し、推奨回路図から、電源側に抵抗とコンデンサを追加する必要があることも分かりました。

### P17-18 電源フィルタ回路の設計
電源には理想的にはまっすぐな電圧がほしいのですが、実際には小さな揺らぎやノイズが乗ります。これが受信結果に影響する可能性があるので、抵抗とコンデンサによる簡易RCフィルタを入れてノイズを減らします。

### P19-20 部品をそろえる
必要な部品を買いそろえました。受信モジュール、コンデンサ、そして抵抗です。ただ、必要な抵抗値が47～100Ωだったのに対して、家にあったのは100Ωと220Ωの抵抗。そこで抵抗の並列接続の公式を使って計算したところ、合成抵抗は68.75Ωとなり、無事に範囲内に収まりました。持っている部品を活かせて嬉しかったです。

### P21 ブレッドボード実配線案
実際に配線しました。通電中は配線をいじらない、電源とGNDの色を分ける、といった基本ルールを守りながら慎重に組みました。「できた～」という達成感がありました。

### P22-24 部品到着／環境のセットアップ
今回使う部品一式が届きました。マイコンや受信モジュールに加えて、次の第二部で使う予定の送信用LEDやトランジスタも一緒に揃えています。開発環境はWindows11とVSCode、MicroPython拡張機能を使ってセットアップし、Lチカ（LED点滅）まで確認しました。

### P25-26 配線できた！
Picoのピン配置を確認しながら、GND・3V3・GPIOへ実際に配線しました。かわいい仕上がりになったと思います。

### P27 どんなコードが必要？
まずは「エアコンのリモコンは、本体にどんな信号を送っているのか」を観察するプログラムを書きました。GPIOのピンの変化（立ち上がり・立ち下がり）を検知するたびに、その時刻とレベルを記録していく仕組みです。

### P28 実験内容・受信データの観察
実際に「停止」ボタンを押してもらって受信させてみると、853個もの時間差データが取れました。冒頭には大きな数値のヘッダー部があり、そのあとに約460マイクロ秒のMARKと、約380または約1220マイクロ秒のSPACEのペアが繰り返されています。広く使われているAEHA規格では「短い方を0、長い方を1」と定義しているらしいので、それに従って読み解いていきます。

### P29 データをもっと分析する
1回の測定だけでは信用できないので、8回試行して統計を取りました。MARKはほぼ460マイクロ秒前後、SPACEは0のとき約380マイクロ秒、1のとき約1220マイクロ秒に集まっていて、ばらつきも小さいことが確認できました。MARKが短いときはその分SPACEが長くなり、1ビット全体の時間（MARK＋SPACE）はほぼ一定という法則も見えてきました。

### P30 0/1への変換
この法則を使って、生データを0と1の文字列に変換するコードを書きました。ヘッダー部とフッター部を除いた424ビット分のデータが取れました。

### P31-35 データの中身を考える
この424ビットの中に、エアコンの設定情報がどう入っているのかを考えます。「操作命令だけ」を送っているのか、「現在の設定全体」を送っているのかという2つの可能性を検証するため、同じ27℃でも「上げて到達した場合」と「下げて到達した場合」の信号を比較する作戦にしました。またモード情報の表し方、温度などの数値の表し方にも複数の候補があるので、8ビットずつ区切って、MSB（上位ビットから読む）とLSB（下位ビットから読む）の両方で解釈してみることにしました。

### P36-38 温度だけを変えて観察
他の設定は固定したまま温度だけを操作し、どのバイトが変化するかを調べました。結果、14・15バイト目が温度、12・13バイト目が上げ下げの方向に対応していそうだと分かりました。さらに14バイト目をLSB読みすると、温度が1℃上がるごとに値が4ずつ増える、という法則を発見しました。これを使って、まだ試していない16℃（最低設定温度）のときの信号を予想し、実際に測定してみたら、見事に的中しました。

### P39 12・13バイト目をみる
上げ下げの操作方向についても、14・15バイト目と同じくLSBに規則性が見られ、13バイト目は12バイト目のビットをすべて反転させた値（補数）になっていることが分かりました。

### P40 データ全体を考えてみる
ここまでの発見から、「値と、その反転値（補数）」を1組として、53バイト全体もそのペア構造になっているのでは、という仮説が立ちました。まだ確認できていないのは残り24組と1バイトです。だんだんウワーッじゃなくなってきました（笑）。

### P41-43 タイマーボタンを調べる
入・切タイマーのボタンだけを操作して、変化するバイトを探しました。切りタイマーは18～21バイト目、入りタイマーは22～25バイト目が対応していて、12・13バイト目は温度の上げ下げのときと同じ、タイマーの有効・無効を表していることも分かりました。実際に計算式を立てて検証すると、「18バイト目と20バイト目を結合した値を16で割って60で割ると時間になる」という規則性が、切りタイマー・入りタイマーの両方できれいに当てはまりました。

### P44 果てしねぇなぁ
ここまで分析を進めることはできますが、ふと本来の目的を思い出しました。分析なんてしなくても、目的の信号さえ再現できればよかったんです。全部のバイトを解読しなくても、冷房ONと停止という2つの信号があれば、最低限やりたいことは達成できます。というわけで、気になる方はぜひ自分でも分析してみてください。

### P45 おわりに：今回学んだこと
今回学んだことは大きく4つです。信号を受信するための38kHz変調や回路設計、データにするためのパルス計測とPythonでの0/1変換、それを読み解くための2進数・16進数・補数・ビットシフトの知識、そして条件を1つずつ変えて仮説と検証を繰り返す実験の進め方です。いちばんの学びは「全部を解読しなくても目的は達成できる」ということでした。目的を思い出して、必要な範囲を自分で決めることも、実験の一部だったんだと思います。

次回は、この受信・解析で得た知識を使って、実際に赤外線を送信し、スマホから操作できるところまで作っていきます。お楽しみに。
